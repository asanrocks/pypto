# Fix campaign — construct-parity findings

Fixes the defects found by `docs/review-constructs.md`. That file stays the
frozen findings record (the `F*` entries with their red checks and pins); this
file is the fix worklist, the contract, and the ledger.

The review campaign proved the divergences exist. This campaign changes
frontend behaviour, which is a different risk class: a fix that makes one
anchor green can silently move another, and the pins left behind by the review
assert the *buggy* behaviour on purpose.

## 1. Contract (every fix task)

`docs/review-r10.md` §1 applies (one task per session, one commit, explicit
paths, the git prohibitions, terse report), with these overrides:

1. **The red check is the F entry's red check**, made to fail *first*. Where the
   review left a pin test asserting the buggy shape, the fix **rewrites the pin
   into the correct expectation and shows it red before touching the frontend**.
   A pin says in its own docstring to delete its assertions when the fix lands;
   that is the instruction, not a suggestion.
2. **Never weaken the oracle.** `tests/ut/language/conformance/_harness.py` is
   not editable; neither is the equivalence notion (or the `INT64`/`INDEX`
   relaxation in `structural_equal.cpp`, which is upstream `45fe19c24`). A fix
   that turns an anchor green by loosening the harness is a failed task.
3. **The full `./scripts/gate` is the acceptance criterion** — unlike the review
   campaign, these tasks change behaviour. Expect it to overflow a session:
   design for resumption, and use `PYPTO_GATE_LOG=/tmp/gate-<task>.log
   ./scripts/gate -- <paths>` for a focused first pass before the full run.
4. **No C++ without saying so.** The IR printer lives in
   `src/ir/transforms/python_printer.cpp`; a task that touches C++ needs a
   rebuild (`scripts/rebuild`) before its evidence counts. Flag it in the
   commit message.
5. **Update the findings record.** Flip the `F*` entry's state in
   `docs/review-constructs.md` in the same commit, and keep the review's
   `needs-decision` wording (do not convert one into a fix silently).
6. **One defect per task.** If two `F` ids are the same defect (F22/F26 are),
   they are one task; if a fix grows a second defect, record it, don't fold it.

## 4. Decision rules (ratified by the human)

The classification that governs every remaining item. It reduces to one
invariant: **tracing ⊇ parser** — R2 grants the tracing lane a superset (parser
limitations are not parity obligations), R4 forbids a subset (whatever the
parser accepts, tracing must accept). R1 and R3 are the only exceptions, and
each is a spec change.

| # | Condition | Ruling |
| --- | --- | --- |
| R1 | invalid Python, or a type lie the AST parser introduced | change the language spec; users take the workaround (`docs/design/`) |
| R2 | valid Python, accepted **only by tracing** (parser limitation) | **no parity goal** — tracing may be a superset |
| R3 | valid Python, but bad typing practice (retyping a variable) | prefer the stricter design — *unless prevalent in existing kernels* |
| R4 | valid Python, accepted by the **parser** | tracing must preserve it: no missing features, no semantic drift, unless a better approach is worth a spec-change commit |
| R5 | both accept, behaviour drifts | trivial drift (redundant assignment, error-message text) is fine; **wrong codegen is not** |

Settled outright by the rules: `return 1.0` / `return t, 1.0` are **host** returns;
`return [a, b]` meaning multi-value is an **R1 type lie** (the spelling goes);
the five acceptance-only leniencies (`pl.static_print()`, `pl.func_attr({...})`,
`pl.at(windowize=1)`, `pl.scope(pl.ScopeMode.MANUAL)`, `pl.cluster(name_hint=1)`)
are **R2/R5 — do nothing**; F11's `std::bad_cast` is the same error-quality class.
**F37 is unblocked** (R4: the parser's 1-tuple reading is the AST-era behaviour).

## 5. Re-triage under the rules

**Batch C shrinks from 6 to 2.** Four of the six "bugs" are exactly what R2
legalises — tightening tracing to match the parser would *remove* capability to
satisfy a parity goal that does not exist:

```python
with pl.scope(mode="manual"):      # parser rejects (not an enum); tracing accepts, picks AUTO
with pl.at(name_hint="has space"): # parser rejects; tracing accepts           -> R2, do nothing
for i in pl.split_aiv(4):
    for j in pl.split_aiv(2): ...  # parser rejects nested;             tracing accepts
```

Dropped as R2-legal (moved to "accepted divergence"): **F19, F21, F24, F25**.
Kept as real subset violations (R4): **F18** (graph drops the parser's forward
sticky `dump_vars`), **F20** (manual-scope depth rules are parser-only). One
sub-question survives: those leniencies emit IR whose printed form does not
re-parse, so the choice is *reject* or *teach the printer* — a printer-coverage
question, not parity. **F36** was kept here as a fix candidate; C3 judged it
under R5 and it is an **accepted divergence (naming-only)** — no fix (see the
ledger).

**F14 (R3) — measured, inconclusive by design.**
`scripts/review/check_rebind_prevalence.py` scans for a dtype change on a name
reassigned inside a loop. Over 268 files / 4742 functions (`examples`,
`tests/st`) plus 540 files / 4444 functions (`pypto-lib`): **5 candidate sites,
an upper bound** — 4 of them in `pypto-lib`'s flagship `qwen3_14b` prefill.
The heuristic reads the first dtype token anywhere in the RHS, so a nested cast
(`pl.assemble(acc, pl.cast(x, FP32))`) over-counts; at least one of the five is
such a false positive worth checking (`prefill_fwd.py:862`). Reading: not
quantitatively prevalent (0.05%), but present in the load-bearing model, so R3's
clause needs a human call rather than a threshold. A precise count needs the
frontends (trace each kernel, compare `Var` types per binding), not a regex.

**Retroactive R4 classification (H1).** B2 (F15), B3 (F16) and B4 (F17)
changed **parser** behaviour, which R4 permits only as a spec change; only B1
had recorded one (`docs/design/01-language.md` §8). Read back against the
commits:

- **B3 (F16) — UNINTENDED, bug fix.** The old parser collapsed an `@pl.inline`
  callee's multi-value trailing return into one `MakeTuple` at the caller's
  return position. §9 (*Multi-value returns keep Python tuple semantics*)
  already states the correct rule — the kernel boundary lowers the elements to
  the IR's multi-value `ReturnStmt`, "neither frontend creates a fictional
  staged-tuple value" — so the parser contradicted an existing spec sentence.
  The fix restores that rule; no spec change.
- **B4 (F17) — UNINTENDED, bug fix.** The old parser captured a nested early
  return's expression and then overwrote it with the trailing return, emitting
  the branch empty and losing its `add` silently. That is silent code loss,
  and the shape is already rejected by both other entrances
  (`CloneInlineBody`; `docs/design/03-entrance.md` §7's one-trailing-return
  contract), so it was an unsanctioned parser artifact. No spec change.
- **B2 (F15) — INTENDED, spec change recorded.** The old whole-body collection
  is the *round-trip reader's* faithful-source reading: the parser is a static
  reader, not an executor, and the review called the reading "defensible and no
  doc decides". The fix chose the traced execution's reading (a function-level
  `return` ends collection), which changes a sanctioned AST-era behaviour
  rather than repairing an accident — the R4 case that needs a spec change. The
  chosen reading is now recorded in `docs/design/01-language.md` §9 (the
  "Trace-time execution determines the IR" rule the fix cites), alongside B1's
  §8 note.

So the spec changes are B1's §8 loop-`else` note and B2's §9 function-level
`return` note; B3 and B4 are bug fixes that needed no spec edit.
